# وضعیت نسخهٔ آزمایشگاهی و اجرای انتشار

تاریخ بررسی اولیه: ۹ نوامبر ۲۰۲۶. استقرار سرور با مالک پروژه است.

## اعلان به‌روزرسانی بازار

در استقرار اول، `BAZAAR_LATEST_VERSION_CODE` خالی می‌ماند. نسخهٔ جدید اندروید در مخزن ۱٫۸ با کد ۹ است. پیش از ارسال، کد را با بالاترین کد ثبت‌شده در پیشخوان بازار تطبیق دهید و به‌روزرسانی از ۱٫۷ را با بستهٔ دارای همان امضای انتشار روی دستگاه بررسی کنید.

بعد از در دسترس قرار گرفتن بسته در بازار، `BAZAAR_LATEST_VERSION_CODE=9` را در محیط اجرای فرانت‌اند تنظیم و سرویس فرانت‌اند را بازآفرینی کنید. مسیر `/api/app-update` باید `{"latestVersionCode":9}` بدهد. روی ۱٫۷ باز کردن آرتین، دکمهٔ بازار و «بعداً» را بررسی کنید. روی ۱٫۸ پیام نمایش داده نمی‌شود. برای توقف اعلان مقدار را خالی کنید و سرویس را دوباره بازآفرینی کنید.

## تکمیل نسخه پیش از تحویل به مخزن

مسیر اصلی محاسبات به محیط آزمایشگاه یکپارچه متصل شد. هر ۹۸ روش بانک قابلیت تشکیل پرونده دارند؛ مسیرهای عددی، کیفی و نمونه‌برداری تفکیک شده‌اند. مدل عددی پایه باید با SOP و شرایط واقعی تطبیق داده شود. میز کار، جست‌وجوی روش، بازخوانی پرونده و گزارش روش تکمیل شدند. تم سرمه‌ای و فیروزه‌ای و انیمیشن ارسالی در قاب واکنش‌گرا اعمال شد؛ پخش واقعی مرورگر و عرض موبایل بررسی شدند.

آخرین بررسی frontend: ۶۱۵ آزمون موفق، build تولید موفق با ۴۸ مسیر. نتیجهٔ backend جدول زیر مربوط به آخرین اجرای کامل ثبت‌شده است؛ در اصلاحات نهایی ظاهر، کد backend تغییر نکرده است. فایل‌های موقت `output/` و آرشیو محلی `frontend/src.zip` جزو تحویل Git نیستند. فایل‌های محیطی و کلیدها باید روی سرور حفظ شوند. CompTox همچنان به کلید EPA نیاز دارد.

## تغییرات این دوره

خطاهای فیلدی توزین با توضیح دسترس‌پذیر و تمرکز نخستین فیلد نامعتبر تکمیل شد؛ همین تمرکز به فرم چگالی اضافه شد. قاب جدول‌های منتخب مواد و مطالعات برای صفحه‌کلید نام‌گذاری و قابل‌تمرکز شد. مشکل بازگشت تمرکز در پنجره‌های ساخت پرونده، جایگزینی نمونه و جایگزینی محلول با hook مشترک اصلاح شد.

آزمون‌های قدیمیِ مشتری/چت اکنون مشتری آزمایشی تأییدشده را از مسیر ورود واقعی استفاده می‌کنند؛ جست‌وجوی دانش با هدر ادمین آزموده می‌شود. شمارندهٔ محدودسازی درخواست پیش از ورود fixture پاک می‌شود تا آزمون‌ها به دفعات اجرای یکدیگر وابسته نباشند. احراز هویت، مجوزها و محدودیت‌های تولید تغییر نکردند؛ آزمون رد درخواست ناشناس برای سه مسیر اضافه شد. قاعدهٔ منع require در ESLint فقط برای اسکریپت‌های CommonJS ممیزی استثنا گرفت.

## نتیجهٔ بررسی‌ها

| بررسی | نتیجه |
|---|---|
| کل آزمون‌های backend | ۵۷۹ موفق، ۲ skipped مربوط به Suncal اختیاری |
| کل آزمون‌های frontend | ۶۱۵ موفق در آخرین اجرای کامل |
| شش آزمون E2E موجود | موفق روی build تولید و سرور موقت 3002؛ backend بخش‌های مربوط mock است |
| build تولید و TypeScript | موفق، ۴۸ مسیر |
| lint کامل frontend | بدون خطا؛ ۱۱ هشدار قبلی برای ناوبری مستقیم و پارامترهای استفاده‌نشدهٔ mockها |
| بررسی secrets ردیابی‌شده | موفق؛ این ابزار فقط دامنهٔ تعریف‌شدهٔ خودش را بررسی می‌کند |
| اعتبارسنجی محیط محلی | صفر failure و ۹ warning |
| اعتبارسنجی محیط production | ۱۱ failure و ۷ warning؛ انتشار باز است |
| Docker Compose config | با متغیرهای ساختگی مخصوص بررسی، بدون خطا؛ اعتبار secrets تولید را ثابت نمی‌کند |
| runtime Docker | اجرا نشد؛ daemon Docker Desktop در دسترس نیست، با بررسی خارج از sandbox نیز تأیید شد |

آزمون کامل backend ابتدا به پوشهٔ موقت محدودشده برخورد کرد و سپس با دسترسی لازم اجرا شد. اولین اجرای کامل، ۱۵ آزمون قدیمی احراز هویت را آشکار کرد؛ عدد بالا نتیجهٔ اجرای کامل پس از اصلاح fixtureهاست. آزمون frontend و build تولید پس از آخرین تغییر رفتاری فرم چگالی اجرا شدند.

## مرور زنده و فایل‌ها

مرور زنده روی سرور توسعهٔ 3000 در مرورگر کنار چت، داخل تب جداگانه با دادهٔ صریحاً فرضی انجام شد؛ تب اصلی کاربر جایگزین نشد. عرض ۳۲۰ پیکسل، مراحل GC فارسی، شش مطالعه، سه ابزار پیشرفته و شش بخش مواد در هر دو زبان بررسی شدند. فرم چگالی در عرض ۱۲۸۰ نیز بررسی شد. ابزار DOM فقط وجود نام برای کنترل‌های نمایان و سرریز افقی کل صفحه را بررسی می‌کند؛ کیفیت همهٔ نام‌ها، کنتراست، حالت نتایج همهٔ فرم‌ها، بزرگ‌نمایی واقعی و انطباق WCAG را ثابت نمی‌کند. رکوردهای اولیهٔ پیش از پایان بارگذاری برای نتیجه‌گیری استفاده نشدند. شواهد: `output/workspace-release-browser-audit.json`.

توزین با جرم فرضی 50 g و U=0.004 g، k=2، گام 0.001 g و s=0.003 g برای n=1 از مسیر سرور نتیجهٔ نمایشی `50 ± 0.007234 g` داد. PDF، HTML و JSON واقعاً دانلود شدند. پس از reload و ورود همان JSON، عنوان، داده و منابع بازیابی شدند و نتیجهٔ قدیمی جاری محسوب نشد. انصراف از پنجرهٔ جایگزینی نمونه داده را حفظ کرد و تمرکز به بازکننده برگشت.

چگالی با اعداد فارسی ۵۰ g و ۲۵ mL و عدم‌قطعیت‌های استاندارد فرضی 0.01 g و 0.02 mL، نتیجهٔ نمایشی `2 ± 0.003298 g/mL` داد. PDF واقعاً دریافت شد؛ تغییر زبان ورودی‌ها را حفظ کرد. فرم خالی نیز تمرکز را به جرم نامعتبر انتقال داد.

دو PDF هرکدام دو صفحه‌اند. هر چهار صفحه با Poppler رندر و بصری بررسی شد؛ متن فارسی و جدول‌ها در نمونهٔ منتخب بدون بریدگی و هم‌پوشانی مشاهده شدند. نسخهٔ دانلودشده، JSON، HTML، تصاویر و SHA-256ها زیر `output/release-*` ثبت‌اند. این‌ها نمونهٔ آزمایشی‌اند و گزارش آزمون واقعی آزمایشگاه نیستند.

## شروط باقی‌ماندهٔ انتشار

1. کلید شخصی EPA باید سمت backend تنظیم شود؛ سپس هویت زنده، شناسهٔ ناموجود و کلید نامعتبر بررسی شوند. توسعه و پذیرش خواص/سمیت/محیط‌زیست بعد از پذیرش هویت همچنان باز است. دادهٔ پیش‌بینی‌شده باید مدل و منبع و واحد جدا داشته باشد.
2. زمان‌سنجی تکرارشده روی گوشی و شبکهٔ نماینده، تعامل و دریافت گزارش و حالت عادی/کاهش حرکت رسانه باقی است. اعداد Chrome روی loopback معیار سرعت گوشی نیستند.
3. مرور صفحه‌خوان واقعی، بزرگ‌نمایی واقعی مرورگر، کنتراست همهٔ حالت‌ها و چرخهٔ کامل صفحه‌کلید همهٔ پنجره‌ها باقی است. شواهد منتخب قبلی پذیرش کامل فناوری کمکی نیستند.
4. محیط مقصد، دامنه و روش استقرار باید مشخص و تأیید شوند. root `.env` لازم برای Compose موجود نیست؛ backend هنوز CORS محلی، ENVIRONMENT توسعه و COOKIE_SECURE غیرفعال دارد. مقادیر واقعی باید در محیط مقصد ثبت شوند. این سند دستور تغییر تنظیمات محلی فعلی نیست.
5. Docker runtime smoke، بازیابی نسخهٔ پشتیبان روی محیط مستقل، TLS، نظارت پس از استقرار و انتشار بستهٔ production Android انجام نشده‌اند. فایل‌های APK آزمایشی پیشین انتشار تولید محسوب نمی‌شوند.

## ترتیب اجرا روی مقصد تأییدشده

این مخزن دو مسیر مستقل دارد: `deploy/` مبتنی بر systemd و SQLite، و Compose مبتنی بر PostgreSQL/Redis/Qdrant. یکی را بر اساس محیط واقعی انتخاب کنید؛ دستور پشتیبان‌گیری PostgreSQL برای SQLite معتبر نیست. نام و مسیر سرویس‌ها در `deploy/` به تنهایی اثبات محیط نصب‌شده نیست.

پیش از هر تغییر، شناسهٔ نسخهٔ در حال اجرا، روش استقرار، نسخهٔ schema، build frontend، مسیرهای runtime و نسخهٔ پشتیبان قابل‌بازیابی ثبت شوند. secrets باید فقط در محل امن مقصد بمانند. snapshot کد فعلی باید شامل فایل‌های جدید و untracked آزمایشگاهی هم باشد؛ HEAD فعلی مخزن به‌تنهایی نمایندهٔ این تحویل نیست. فایل manifest این نوبت فقط اثرانگشت منابع منتخب را ثبت می‌کند و بستهٔ نصب کامل نیست.

ابتدا بازیابی نسخهٔ پشتیبان روی دیتابیس مستقل و راه‌اندازی نسخهٔ قبلی در محیط آزمایش تأیید شود. فایل‌ها/آپلودها و بانک دانش نیز با همان نسخه هماهنگ نگهداری شوند. روی SQLite از backup API یا ابزار آنلاین سازگار با WAL استفاده شود؛ کپی تنها فایل app.db هنگام نوشتن کافی نیست. برای PostgreSQL، dump و بازیابی آزمایشی با ابزار همان نسخه لازم است.

پس از پشتیبان معتبر، همان artifact بازبینی‌شده روی staging ساخته و اجرا شود. build باید NEXT_PUBLICهای محیط مقصد را داشته باشد؛ تغییر صرف متغیر runtime لزوماً کد مرورگر از پیش buildشده را تغییر نمی‌دهد. health، دسترسی ادمین/مشتری، رد درخواست ناشناس، محاسبهٔ GC/توزین/چگالی، دانلود PDF/HTML/JSON و بازخوانی JSON کنترل شوند. در Compose، nginx/SSE/WebSocket و health همهٔ سرویس‌های مورد استفاده نیز بررسی شوند. سپس TLS، آلارم‌ها و مسیر production کنترل شوند.

## بازگشت از انتشار ناموفق

محرک بازگشت: خطای پایدار health، شکست ورود، اختلاف نتیجه با مثال مرجع، خرابی فایل/گزارش یا افزایش خطای مسیر بحرانی. ترافیک جدید و نوشتن داده متوقف یا محدود شود و لاگ خطا بدون secrets حفظ شود. نسخهٔ فعلی حذف نشود؛ artifact قبلیِ ثبت‌شده با تنظیمات امن خودش اجرا شود.

اگر schema سازگار باقی مانده است، کد و build قبلی با دادهٔ جاری آزموده شوند. اگر مهاجرت ناسازگار انجام شده، بازگشت کورکورانهٔ دیتابیس ممنوع است: ابتدا نسخهٔ جاری داده‌ها حفظ و اثر ازدست‌رفتن نوشته‌های پس از backup مشخص شود؛ بازیابی باید از نسخهٔ پشتیبان آزمایش‌شده و با تصمیم صریح انجام شود. بازخوانی JSON و صحت دانلود گزارش پس از بازگشت دوباره کنترل شود. تکمیل این runbook جای اجرای واقعی restore یا rollback روی مقصد را نمی‌گیرد.
